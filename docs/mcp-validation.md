# MCP 接入验证

日期：2026-10-19，Asia/Shanghai。环境：Windows、Node.js 24.14.0、Codex 内置浏览器、官方 MCP TypeScript SDK 服务端 / 客户端 2.3.1。

## 本轮实现

- 顶栏新增非模态“AI 接入”面板，默认只读，按当前单张画布开启；提供临时 stdio 客户端配置、收起与断开。
- 工具为 `get_canvas`、`edit_canvas`、`connection_status`。支持卡片新增、修改、删除、建立连接及删除连接，一批最多 50 项。
- 写入要求内容 revision，先在副本中校验，提交前重查原会话授权、请求有效期、整个工作区及本页状态；保存成功才替换内存和回执，整批可撤销。
- 本机桥只转发临时请求，不保存画布。owner / client 令牌分离，只存当前会话；原存储键、v1 JSON 及旧六步工具保持兼容。
- 冲突时收起面板并断开授权，恢复入口可直接操作；开启、断开及 Esc 的焦点保持在对应控件，避免快捷键误操作背后卡片。

## 自动检查

`npm run verify` 通过静态检查及全部 98 项测试：原有 66 项、MCP 纯操作 21 项、桥与协议 11 项。`git diff --check` 通过。

新增检查包括：批内引用和原子回滚、内容版本冲突、旧字段保留、文本安全、容量与输入限制；Host / Origin、自定义头和令牌角色隔离、只读拒写、队列上限、断连、心跳和会话到期、单次交付及超时清理；真实 SDK stdio 初始化、工具发现和调用。poll 返回的操作截止时间取请求、会话及心跳期限的最早值，虚拟时钟测试覆盖临近到期边界。

UI 模块对延迟操作的撤销、同画布重新授权、期限与焦点转移另做临时逻辑检查和代码复审；这些检查没有替代下面的真实浏览器流程。

## 真实浏览器与 MCP 客户端

在独立源 `http://127.0.0.1:4191/` 使用虚构内容；客户端通过页面实际生成的配置启动 `scripts/mcp-server.mjs`，调用经过 stdio → 本机 HTTP 桥 → 浏览器 → 保存与回执的完整链路。没有在正式源 `http://127.0.0.1:4176/` 开启授权或操作真实画布，也没有清空 localStorage。

| 路径 | 实测结果 |
| --- | --- |
| 默认与只读 | 面板默认只读；真实客户端发现三个工具，读取一张卡片的画布，写入返回 `read_only` |
| 批量编辑 | 一个请求创建两张卡片及两条连线，页面显示三卡两线；一次撤销回到一卡零线，重做恢复三卡两线 |
| 版本与编辑保护 | 旧 revision 写入返回 `revision_conflict` 且未新增；用户编辑器仍打开时返回 `canvas_busy`，文字与折叠光标均保留 |
| 修改与删除 | MCP 修改卡片文字、颜色和位置，并删除指定连线；整批撤销恢复。删除中间卡片会清理其两条线，一次撤销可恢复三卡两线 |
| 授权撤销 | 手动断开、切换画布和授权后刷新，旧客户端调用均返回 `unauthorized`；界面配置清空，不在新画布自动恢复 |
| 面板与键盘 | 收起不停止有效接入；Esc 归焦入口；开启成功聚焦断开按钮，断开聚焦权限选择。背后选中卡片时，面板内 Delete / Ctrl+Z 不改卡片 |
| 刷新保存 | 等待保存后刷新，标题、文字、卡片 ID、位置、颜色、连线 ID 与路径、视图变换均与刷新前一致 |
| 跨页冲突 | 本页正在编辑，另一页修改并保存后，本页暂停覆盖，接入凭据清空、面板自动收起；无需手动关面板即可保留副本，双方文字均可在副本中找到 |
| JSON 兼容 | MCP 编辑后的三卡两线经真实下载再追加导入；卡片、颜色、位置与关系保留，原画布保留。下载文件仍为原 v1 字段，没有授权或会话字段 |
| 本机操作回归 | 断开后 Tab 延伸、原位编辑、拖动、删卡、撤销与重做正常 |
| 窄屏 | 模拟 320×720 CSS 视口，页面无横向溢出；面板 x=12…308、y=168…523，可内部滚动；配置文本框 x=29…276，没有超出面板 |

浏览器控制台未记录警告或错误。示例截图：[MCP 接入面板](../assets/screenshots/mcp-connection.png)，只含虚构内容，客户端配置已折叠，未展示令牌。

交付前核对正式端口的服务身份、源码目录与进程后，重启了本项目 Node 服务，保持 `http://127.0.0.1:4176/`。页面返回 200，未携带令牌的 MCP 调用返回 401；没有自动开启任何真实画布授权，也没有刷新用户原页面。

## 验证边界

没有自动修改或安装用户的 AI 客户端全局配置，也没有把当前聊天报告成已加载新工具；实际协议接入使用官方 SDK 客户端验证。未连接云端模型服务，未验证其他客户端的设置界面、真实触控设备或其他浏览器。

请求期限、授权撤销及会话到期由自动测试、临时 UI 逻辑检查和代码复审共同覆盖；未在真实浏览器中注入长时间 Web Lock 占用、系统休眠、存储配额耗尽或断电。若修改已保存但回执丢失，应先重新读取再重试，不能承诺网络中断后的调用一定未生效。旧六步源码未改，未重跑其完整界面流程。

## Codex 客户端配置与验证（同日追加）

用户随后明确要求配置当前 Codex 并验证读取、编辑。以下是独立于上述 SDK 验证的新结果，不改变前一轮记录的范围。

- 将 `yuandian` 作为 stdio 服务加入当前用户的 Codex `config.toml`。修改前在客户端目录备份；最终保留原文件全部字节，仅追加该服务及其环境变量。`codex mcp get yuandian --json` 能读取已启用配置；核对输出不包含令牌。
- 在正式入口 `http://127.0.0.1:4176/` 新建虚构的“Codex MCP 接入验证”画布，仅对该画布开启读写授权。未重置站点数据，未用 MCP 修改其他画布。
- 通过本机同版 `codex app-server --stdio` 建立临时、不落盘的验证上下文；没有运行模型回合，也没有创建持久用户聊天。调用 Codex 的 `mcpServerStatus/list` 发现 `connection_status`、`get_canvas`、`edit_canvas`，实际工具调用使用 `mcpServer/tool/call`。

| 路径 | 实测结果 |
| --- | --- |
| 状态与读取 | `connection_status` 返回读写权限；`get_canvas` 返回指定测试画布的一张卡片及内容版本 |
| 编辑 | 使用读取到的 revision，在一批操作中修改原卡片、创建一张绿色卡片并连接两卡；结果为两卡一线，页面显示已保存 |
| 版本保护 | 使用旧 revision 再次编辑返回 `revision_conflict`，过期文字没有保存 |
| 撤销与重做 | 在授权页点一次撤销，回到原来的一卡零线；重做恢复两卡一线 |
| 持久化 | 完成保存后打开另一张同源页面，重新加载出的测试画布仍为两卡一线 |
